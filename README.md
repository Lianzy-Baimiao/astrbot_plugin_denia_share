# 希望解析器

支持多平台链接解析，并自带一个网页界面（WebUI）：把分享链接解析成结构化内容，渲染成分享卡片发出来。

支持 **B站 / 抖音 / 快手 / 微博 / 小红书 / Twitter(X) / AcFun / NGA / GitHub / Pixiv / Steam**
十一个平台，另有网页截图（`/shot`）与 Pixiv 搜索（`/pixiv`）。不够用还可以自己加平台，
见[自定义解析器](#自定义解析器)。

## 各平台解析什么

| 平台 | 内容 |
| --- | --- |
| B站 | 视频 / 动态 / 直播 / 专栏 / 收藏夹 |
| 抖音、快手 | 视频 / 图集 |
| 微博 | 正文 / 视频 / 长文 |
| 小红书 | 笔记（图文 / 视频），图片与封面统一改写为无水印原图 |
| Twitter / X | 推文（图片 / 视频） |
| AcFun | 视频 |
| NGA | 帖子 |
| GitHub | 仓库卡片：星标 / 分支 / 未关闭 issue / 主语言 / 许可 / topics / 最近提交 |
| Pixiv | 作品；`xRestrict != 0` 的内容**一律拦截**，不提供开关 |
| Steam | 商店页：名称 / 简介 / 开发商 / 发行日期 / 类型 / 国区价格 / 折扣 |

结果会渲染成分享卡片（**4 种布局 × 深浅双主题**），也可以在配置里关掉、回退纯文本。
另外支持 QQ 小程序分享卡片（OneBot `Json` / 官方平台原始卡片字段）里的链接提取，以及 OneBot 合并转发发送。

聊天接入支持 **OneBot（aiocqhttp / NapCat 等）** 与 **QQ 官方 Bot**（`qq_official` /
`qq_official_webhook`），两者的发送差异见[接入方式差异](#接入方式差异onebot-与-qq-官方-bot)。

## 安装

1. 把 `astrbot_plugin_denia_share` 放进 AstrBot 的 `data/plugins/` 目录
2. 安装依赖：`pip install -r requirements.txt`
3. **装 ffmpeg**：视频处理要用它（B站高清的音视频合并、AcFun 等 m3u8 分片重封装成标准 MP4、
   视频没有现成封面时抽帧）。没装也能跑，但这几项会降级：m3u8 只做裸拼接，电脑版 QQ 可能放不出来
4. 重启 AstrBot，在插件管理里启用

> 自带的网页界面需要 AstrBot **>= 4.25.3**。更老的版本插件照常工作，只是没有这个页面。

## 用法

**群里直接发链接就会被解析**，不需要命令。命令只有这几条：

| 命令 | 作用 | 权限 |
| --- | --- | --- |
| `/shot <网址>` | 网页截图 | 全部 |
| `/pixiv <关键词>` | Pixiv 搜索，最多 6 张，强制过滤非全年龄 | 全部 |
| `/bili_login` | B站扫码登录（想下 1080P 及以上才需要） | 管理员 |
| `/bili_check` | 检查 B站 Cookie 是否有效 | 全部 |
| `/denia_status` | 查看插件运行状态 | 管理员 |
| `/denia_clear` | 立即清空解析缓存 | 管理员 |

### QQ 官方小程序卡片没有反应？

先在同一个会话直接发 BV 号或分享链接。直接输入能解析、卡片不能解析，通常需要检查卡片的接收格式，而不是重新配置 Cookie。

插件除了 OneBot JSON，还会检查官方消息当前卡片的 `raw_message` / `raw_data`、ARK、JSON 内容、`msg_elements` 和小程序页面路径。v1.3.11 补齐正式的 `ark_data.fields.jump_url` 入口；提取到可识别的链接或 BV 号后复用正常解析流程。不会解析引用中的旧卡片，也不会按标题搜索猜视频。

如果接口 / 宿主只保留了标题、来源图标和预览图，这些信息不足以可靠确定视频。插件会保持群内安静，在 AstrBot 日志记录 **`QQ官方卡片未匹配到已启用平台的链接/BV号`**，附带原始对象类型、候选数量、已检查的固定字段名与是否触及读取上限。日志不回显原始消息、标题、URL、用户标识或凭证。

**有目标链接与只有卡片摘要是两种情况：**

- 当前卡片的 `ark_data.fields.jump_url` 含启用平台的链接：复用正常解析流程；SDK / Webhook 两种接入均支持，签名参数和分 P 保留。
- 当前可见卡片只有 `preview`、`source`、`source_logo`、`title`，其他已检查字段也没有链接 / BV：不能可靠确定视频，不按标题搜索或拿预览图猜测；请直接发 BV 号或分享链接。
- `候选=0` 仅表示插件在自己的可见输入中没有提取到目标，不能证明 QQ 服务端从未下发链接；`候选>0` 仍未匹配还需检查该平台解析器是否启用。

已针对 **AstrBot 官方 v4.28.2 + qq-botpy 1.2.1** 核查并回放接收链路：原版适配器将事件数据保存在 `raw_message.raw_data`，不会单独裁剪 `ark_data`；含 `ark_data.fields.jump_url` 的合成卡片可到达插件并触发解析入口。该版本的转换方法也没有按卡片字段拼装上述摘要。此结论不等于已获得实际服务器报文，也不覆盖第三方修改版。

v1.3.10 的临时字段结构探针已在 v1.3.11 移除，不需要为同一张缺少目标的卡片反复安装诊断包。若继续追查信息在哪一层丢失，需要对照官方适配器转换前的卡片字段，而非只在分享插件里扩大扫描范围；不要提供含身份、Cookie、Token 或 `message_scene` 鉴权信息的整包报文。

## 网页界面

Dashboard 侧边栏「插件 WebUI → 希望解析器」，分五个标签：

| 标签 | 用途 |
| --- | --- |
| **总览** | 运行状态、B站扫码登录、平台一键开关（含自定义解析器的启停） |
| **解析** | 手动粘贴链接预览卡片（可临时换主题 / 布局），网页截图小工具，自定义解析器管理 |
| **缓存** | 解析记录的搜索 / 筛选 / 分页 / 预览 / 删除，以及缓存清理 |
| **外观** | 上半改网页观感，下半是卡片设计器（右侧实时预览，边调边看） |
| **配置** | 全部配置项，按大类分组、可折叠、可搜索 |

配置改完**保存即生效**，不需要重载插件。

**两套「外观」是刻意分开的**：界面自定义只改你自己看到的这个网页，卡片设计器改的才是
真正发出去的卡片。

## 配置

配置项都在网页界面的「配置」页里维护，分 9 组、带说明、可搜索，不用手改 json。
最常动的几项：

| 项 | 默认 | 说明 |
| --- | --- | --- |
| `DISABLED_PLATFORMS` | 空 | 关掉不想解析的平台，逗号分隔 |
| `VIDEO_DURATION_MAXIMUM` / `VIDEO_SIZE_MAXIMUM_MB` | 480 秒 / 100 MB | 超限不下载视频，卡片照发 |
| `SEND_MODE` | 三项全选 | 独立多选：`文本` / `卡片` / `富媒体`，可任意组合；卡片还需开启渲染总开关 |
| `SEND_MODE_OVERRIDES` | 空 | 按群 / 平台覆盖发送选项，如 `972781741=文本+卡片`、`qq_official=文本+富媒体`；优先级 umo > 群号 > 平台名 > 全局默认 |
| `TEXT_TEMPLATE` | 空 | 「文本」那条消息的模板（如 Markdown），占位符 `{title}` `{url}` `{info}` `{warnings}` `{summary}` `{cover}` `{play_url}` `{platform}` `{author}`，占位符全空的行整行省略；QQ 官方 Bot 按 Markdown 渲染，OneBot / NapCat 下 `![](…)` 换成真图片、`[文字](地址)` 换成「文字：地址」单独一行。留空 = 默认精简文本 |
| `BLACKLIST_ADMIN_EXEMPT` | 开 | 管理员是否豁免黑名单；关掉后黑名单也能拦住管理员，用来做「这个群连我自己都不响应」 |
| `BILI_CODEC` | H264兼容 | B站只取 H.264 流 —— 电脑版 QQ 放不出 HEVC/AV1，会出现花屏；改 `全部编码` 才能拿 4K/8K |
| `OFFICIAL_RELAY_FIRST` | 关 | 官方 Bot 视频**优先**试中转链接（不推荐，见下）；默认走本地分片上传 |
| `OFFICIAL_VIDEO_OPTIMIZE` | 开 | 官方 Bot 的抖音优先下载接口提供的最低码率版本；所有平台超过 28 MB 的视频先压缩，避免 QQ 降级成群文件；需要 ffmpeg + ffprobe |
| `OFFICIAL_CHUNK_PAD_MIN_MB` | 4 | 官方 Bot 上这个体积以上（且 ≤10MB）的视频补位到分片上传，专治「上传文件API返回None」重试 |
| `SEND_ERROR_MESSAGES` | 关 | 解析失败要不要在群里回一句；关了更安静 |
| `BILI_CK` | 空 | 建议用 `/bili_login` 扫码，配了才能下 1080P 及以上 |
| `PROXY` | 空 | 全局代理，作用于媒体下载与自建请求 |
| `GITHUB_TOKEN` | 空 | 建议填：免 token 只有 60 次/小时，且按出口 IP 计，共享 IP 下极易被限流 |
| `CACHE_TTL_HOURS` | 24 小时 | 缓存保留时长，0 = 不自动清理 |

其余（Steam 地区与史低 key、网页截图后端、卡片外观、媒体发送、小红书 / Pixiv Cookie 等）
都在那一页里。卡片外观建议直接在「外观 → 卡片设计器」里调。

## 发送模式

「媒体发送 → 发送模式」现在是**三个独立的多选框**，文本和卡片不互斥：

| 选项 | 发送内容 |
| --- | --- |
| `文本` | 1 条精简文字：标题 + 干净地址 + 简洁播放信息 |
| `卡片` | 渲染的分享卡片图片；还需开启「卡片外观 → 启用卡片渲染」 |
| `富媒体` | 原始图片 / 视频 / 音频，不包含分享卡片 |

默认三项全选，可任意组合。例如：

- **文本 + 卡片**：既有可复制的文字链接，也有分享卡片，不发原始媒体。
- **文本 + 富媒体**：1 条精简文字，再发送原始图片 / 视频 / 音频，不发卡片。
- **仅勾选卡片**：只发送分享卡片（卡片渲染总开关也必须开启）。
- **全部取消**：不发送解析产物。解析、下载行为不变，不节省下载带宽。

**卡片选项与卡片渲染总开关同时开启才发卡片**；关闭总开关不会强制开启文本，
也不会关闭富媒体。旧版 `全部发送` / `文本+富媒体` / `仅文本` / `仅富媒体`
会自动转换为对应的勾选项，保留 v1.3.6 的发送组合。

勾选文本时，分享摘要只发一条，不使用「聊天记录」合并转发，通常只有三行：

```text
视频标题
https://www.bilibili.com/video/BV123?p=2
⏱ 3:25 · 播放 12.3万
```

去掉分享追踪参数，但保留分 P、定位参数、访问凭证等必要信息；没有的播放信息不占行。
不再附带长简介、AI 总结、作者头或整排互动统计；缺少标题时以截短的正文作为标题。
基础信息一到就先发送这条文字，再处理卡片、原图、视频 / 音频；不会为等待媒体下载、合并或缺料检查而扣住文字。
B站标题、时长、播放量请求不再先等待 Cookie 联网校验 / 刷新；下载仍正常校验凭证。
AI 总结、在线人数仅在实际渲染卡片时补充，并行请求、最多等待 5 秒，不影响文字。
文字仍需等待平台基础信息接口返回，并不承诺网络请求零延迟。

发文字时已知的限制提示（例如时长超限）可并入同一条；之后才发现的下载失败记录到日志 / 卡片，不补发第二条摘要。
仅文本或全部取消时，交付流程不等待后台媒体任务；解析器已启动的下载行为保持不变。

只对某个群 / 平台改？用「媒体发送 → 按会话覆盖发送模式」，每条写 `键=选项+选项`：

```text
972781741=文本+卡片
21E86DB833C12870E3287DF3C5704B5F=文本+富媒体
qq_official=文本+卡片+富媒体
123456789=不发送
```

覆盖值支持三个选项的任意组合，`不发送` 表示全部关闭，兼容旧版模式名。
键可以填群号、官方 Bot 群 openid、平台名（`aiocqhttp` / `qq_official`）或完整
umo（`aiocqhttp:GroupMessage:972781741`）；优先级 **umo > 群号 > 平台名 > 全局默认**，
都没命中就走全局。覆盖中的卡片也受总开关控制。
写错的条目只跳过自己并记一条日志，不会连累其它群。

## 黑白名单

「权限控制」里白名单 / 黑名单各管用户与群，判定顺序：

    管理员 > 用户白名单 > 用户黑名单 > 群白名单 > 群黑名单 >（白名单开启则拒绝，否则放行）

- **两种 ID 格式都支持，且大小写不敏感**：NapCat 是数字群号（`972781741`），
  QQ 官方 Bot 是 32 位十六进制串（群 `21E86DB833C12870E3287DF3C5704B5F`，用户同理），
  直接粘进名单即可，openid 大小写随便写都能命中。
- 同一个「群」在两个平台上是两套 ID：**想让两个接入都放行 / 都拦，两个 ID 都要写**。
- **管理员 = AstrBot 全局 `admins_id` 名单**（不是 QQ 群里的管理员身份）：NapCat 那边填 QQ 号，
  官方 Bot 那边填用户 openid。管理员默认**豁免黑名单**；想连管理员都不响应（比如自己的测试群），
  把「黑名单 → 管理员豁免黑名单」关掉即可。
- 私聊没有群号，群名单对它不生效；只配了群白名单时私聊会被拒。

## 接入方式差异：OneBot 与 QQ 官方 Bot

两类接入都能用，日常行为一致，差别只在「媒体怎么交出去」：

| | OneBot（aiocqhttp / NapCat 等） | QQ 官方 Bot |
| --- | --- | --- |
| 合并转发（长文 / 多图） | 支持 | **不支持** —— 框架会丢弃该消息段，插件自动退化成普通消息 |
| 视频 | 协议端读本地路径，不在同一容器时要共享目录或媒体中转 | 框架把本地文件上传给 QQ（base64 / 分片），**默认不需要公网** |
| 图片 / 语音 | 正常 | 正常（这两类框架本来就转 base64） |
| 频道消息 | — | 不支持视频（框架限制） |

QQ 官方 Bot 的视频由插件**主动发送**（只有主动发送的异常才会回到插件手上，从而能补救），
默认顺序是「**本地分片上传 → 中转链接兜底 → 文字兜底**」，详见下一节。
若你想反过来，把「媒体发送 → 官方 Bot 视频优先用中转链接（不推荐）」打开。

### 官方 Bot 视频太大变成群文件？

QQ 官方《群聊富媒体上传》文档规定：视频软限制 **30 MB**，超过软限制会降级为文件。
这与「是否分片上传」不同；指定视频类型也不能绕过大小限制。

v1.3.15 默认开启「媒体发送 → **官方 Bot 视频低码率与压缩**」：

1. **抖音优先最低码率**：SSR 分享页和 Web API 两条路径都从实际返回的多码率列表中选小码率；若没有多档，使用已有直链，不伪造清晰度参数。低码率地址失效时有限次尝试备用地址。
2. **发送前检查大小**：官方 Bot 上所有平台的视频超过 **28,000,000 字节（28 MB）** 时，使用 ffmpeg 两遍编码，H.264 + AAC、画面最长边不超过 640 像素、24 fps，按完整时长计算码率并预留余量；必要时再降一次码率。不会截断尾部。
3. **验证后再发**：检查实际大小、时长、视频编码与音轨是否保留；本地上传和中转链接都使用压缩后的文件。压缩副本缓存复用，原下载文件不覆盖；同一时间最多压缩一条，取消任务会终止编码器。
4. **失败不悄悄发群文件**：未安装 ffmpeg / ffprobe、编码失败或压后仍超限时，发原因提示和原分享链接，不上传超限原文件。

需要在 **AstrBot 所在主机或容器** 安装 ffmpeg 和 ffprobe，并让两者在 PATH 中可执行。
已有下载大小 / 时长上限仍有效：超过下载上限的资源不会先下载再压缩。
OneBot 与 WebUI 保持原有画质策略，解析缓存与官方低码率缓存隔离。
关闭该开关可恢复原行为，但大视频仍可能被 QQ 展示成群文件。

### 官方 Bot 视频发送：为什么默认是「本地上传 + 分片」

框架把本地视频交给 QQ 时有两条路，**只由文件体积决定**（AstrBot `>=4.28`）：

| 体积 | 框架路径 | 单请求超时 |
| --- | --- | --- |
| **≤ 10 MB** | 单次 base64 POST 到 `api.sgroup.qq.com` | **20 秒** |
| **> 10 MB** | 分片上传（5 MB/片、4 路并发、预签名 COS 地址） | 300 秒 |

而 QQ 官方文档也写明**本地文件推荐分片上传**。所以上行稍慢（base64 体积 ≈ 文件的
1.37 倍，20 秒装不下）时会出现：

```
APIReturnNoneError: 上传文件API返回None，触发重试      ← 每 20 秒一次，退避 2/4/8/16 秒重试 5 次
```

**这不是格式或大小被 QQ 拒绝**（那会是秒级错误码 `850031` / `850019`）。插件的做法：

1. **默认本地分片**：`≥4 MB`（且 ≤10 MB）的视频先被追加一个合法的 MP4 尾部 `free`
   box，补到略超 10 MB → 落到分片上传（把文件直接推进 QQ 的预签名 COS 地址，
   没有一次性状态、单请求 300 秒）；体积本就 >10 MB 的直接走分片；
2. 本地失败 → 补位重试一次，并把「本机单发不可靠」写进插件数据目录
   （之后 ≤10 MB 的视频一律走分片，重启仍有效）；
3. **链接兜底**（可选）：注册成 `{AstrBot 回调地址}/api/file/<token>` 交给 QQ 服务器拉；
4. 仍然失败 → 发一条带**原链接**的文字，不让消息彻底消失。

> **补位补的是什么**：文件**末尾**追加一个 MP4 `free` box（规范里的「空闲区」），
> 视频本体一个字节都不动。实测对比（8.5 MB 的 B站视频 → 补到 10.06 MB）：
> 前 8,894,110 字节 `cmp` 完全相同、时长 38.382653 秒不变、帧数 1151 帧不变、
> `ffmpeg -f null -` 完整解码零错误。代价只是多传 1.58 MB +
> 缓存目录多一份 `<名字>.qqchunk.mp4`（跟随缓存 TTL 清理）。

> ⚠️ **两个框架级的坑**（都是实测踩出来的，插件里已绕开）：
> 1. **文件 Token 一次性**：`file_token_service.handle_file()` 取一次就 `pop`
>    （源码注释「使用后令牌失效」）。QQ 拉取只要有一次没拉完，框架的后续重试全部
>    404 —— 所以「让 QQ 来拉」的链接路径对视频不可靠，只做兜底。
> 2. **`send_by_session` 永远不发 msg_id**：官方适配器把
>    `_allow_group_proactive_send` 硬编码为 `True`，于是 `if msg_id and not
>    allow_group_proactive_send` 永不成立 → 经 `context.send_message` 发给群的消息
>    一律算「主动消息」，没申请权限的机器人会收到 `主动消息失败, 无权限`。
>    插件因此在官方 Bot 上改用 `event.send()`（带**入站 msg_id** 的被动回复），
>    卡片与视频都走这条路。

另外两个 QQ 侧的硬事实：**视频 mp4 软限制 30 MB**（超过会降级成「文件卡片」，
能发但不能直接播）、硬限制 200 MB；图片 / 语音软限制 20 MB。单聊与群聊的上传接口
互相独立，上传的文件不能跨场景使用。

（超过会降级成「文件卡片」，仍然能发，只是不能直接播放）、**硬限制 200 MB**；

## Docker 分容器部署：视频发不出去

AstrBot 把图片和语音转成 base64 发出，**视频却是原样带文件路径**（`file:///...`）——
所以 AstrBot 与 NapCat 等协议端不在同一个容器时，图文和语音正常，只有视频发不出去。
两种解法，配一个即可：

**① 共享缓存目录** —— 配「媒体发送 → 共享缓存目录」填一个容器内路径，并让所有相关容器
把宿主机同一个目录挂到**同一个绝对路径**上，例如：

```yaml
services:
  astrbot:
    volumes:
      - /srv/astrbot/data/shared:/app/sharedFolder/denia_share   # 用绝对路径
  napcat:
    volumes:
      - /srv/astrbot/data/shared:/app/sharedFolder/denia_share   # 必须是同一路径
```

然后配置里填 `/app/sharedFolder/denia_share/cache`。

**② 媒体中转** —— 配「媒体发送 → 启用媒体中转」，把下载好的视频注册成 AstrBot 的临时
HTTP 链接再发送，协议端只要能访问那个地址就行，**不需要共享挂载**；同一 Docker 网络里
可直接填 `http://astrbot:6185`。

> 这一节只针对 OneBot / NapCat 这类协议端。QQ 官方 Bot 由框架自己上传本地文件，
> 默认不用中转，见[接入方式差异](#接入方式差异onebot-与-qq-官方-bot)。

两种方式失败都会**回退成本地文件发送**，不会把视频丢掉。总览页检测到「在容器里但两条路
都没铺」时会给出提示。

## 自定义解析器

想加第 12 个平台（或改掉某个内置平台的行为），不用改插件代码：把一个 `.py` 文件放进
插件数据目录的 `custom_parsers/`，点网页界面「解析 → 自定义解析器」的「重新加载」即生效，
之后群里发链接一样会被解析。

**说明就在那个目录里** —— 首次运行会写入一份 `README.md`（用法、与内置平台的优先级规则、
接口版本、加载失败原因）和一份 `TEMPLATE.py.txt` 模板，复制模板改一改即可。
加载状态与失败原因显示在「解析 → 自定义解析器」卡上，不用翻日志。

> ⚠️ 那个目录里的文件会被**直接执行**，权限等同于插件自身。只放自己写的、或完整读懂的代码。
